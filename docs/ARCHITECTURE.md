# Current architecture and integration seams

## Preserved prototype

The client is a browser-only, render-to-DOM JavaScript interface. Its `state` is initialized from fictional seed data or the `lumaco_prototype_v3` localStorage key. Navigation and panels are generated by renderer functions and click/submit/change event delegation. This approach preserves the existing working demo but is not a scalable server-sync architecture.

The original monolithic script has been extracted into seven ordered classic JS files. These are **not ES modules** yet: cross-file globals and deliberate renderer overrides remain, requiring the order documented in `index.html`. Avoid rearranging or bundling without first writing behavior tests.

## Local development backend

`backend.server` serves the frontend and minimal JSON endpoints. `database/schema.sql` models workspaces, companies, contacts, identities, projects, interactions, promises, integration coverage, and audit events. It uses SQLite for convenience. Endpoints are intentionally **local development only** and expose no authentication or workspace isolation; backend and frontend are currently separate data stores.

`backend.logic.classify_interaction` demonstrates contact threshold and outreach/engagement rules using declared event metadata. It does **not** classify text using AI. Real extraction will need connector API permissions, deduplication, vendor-specific webhooks/polling, explicit provenance and human correction.

## Proposed production services (future, not built)

- Auth + Organizations: login, user identity, member/manager roles, workspace boundaries.
- Integration service: OAuth tokens held server-side, scoped Gmail/Outlook/calendar sync and webhook handling, rate-limit/retry logic.
- Identity matching: exact approved email/phone match; uncertain matches presented for review.
- Activity engine: canonical interaction events, outreach/engagement rules, independent cadences.
- Promise engine: extraction from approved sources, source evidence, confidence, deduplication, correction and lifecycle.
- Relationship context: snapshots, meeting briefings, approved contact timelines and company summaries.
- Notification service: event queue, deduplicated Needs Attention, digest, snooze and Focus Mode.
- Manager reporting: authorized company-workspace records only; separate missing-source coverage labels.

## Data visibility rules

Personal-only material must be stored in an identity-isolated personal workspace, *not* merely hidden from a manager's UI. Team and manager views need server-side permission checks. Do not generate manager reports from private notes, directly **or indirectly** through computed metrics or AI summaries.

For a company-owned account, the employer's own access/retention policies may apply. App settings cannot promise absolute privacy over information in an employer-controlled system.

## Recommended development migration

1. Freeze the behavior with browser regression tests.
2. Extract models and business rules into separately tested modules.
3. Add auth and role checks before moving real contact data to a server.
4. Move browser-only state to authenticated API with explicit migration/export.
5. Add **one** proven connector, and report source coverage honestly.
6. Integrate manager reporting only after real authorization controls.
